# REQUIREMENTS.md — SextantDrift 产品需求规格说明书

> **版本**：v2.0（2026-10-19）
> **性质**：当前已落地行为的需求基线。写的是系统现在必须做到什么，以及怎样验收。
> **相对 v1.0**：补上业务需求图的定稿；架构门禁、验收证据、离线报告分开写清。三轮熔断仍是使用者的操作习惯，不是产品功能。

唯一可写的规范是仓库里的 `sextant.json`。图、Mermaid、终端清单都是它的只读投影。

---

## 1. 问题与用户

人审不过来 AI 写出的代码。行级 diff 看不到跨层调用，画完的设计图也不会跟着代码走。

| 角色 | 要完成的事 |
| :--- | :--- |
| 写代码的人和协助他的 Agent | 五秒内知道这次改动有没有越过已声明的架构边界，并拿到文件和行号 |
| 看需求的人 | 从一条需求出发，看懂它直接连着什么，并认出还没关闭的问题和缺锚点 |
| 看 CI 的人 | 用退出码挡住新的架构偏航；验收证据单独给出，不和架构检查混成一个结论 |

---

## 2. 这一版交付的四件事

1. **架构门禁**：从源码 AST 提取依赖，对照 `sextant.json` 里的分层与不变量，报告旁路、逆向依赖、循环依赖和禁止导入。
2. **业务需求浏览器**：在同一份配置里声明需求、流程、规则、事件、状态、代码和验收，报告按一个实体的直接邻居来读。
3. **离线审查报告**：`report` 生成单文件 HTML。架构图是原生 SVG。业务区是目录加邻居图。不请求网络。
4. **验收证据**：`verify` 跑项目里已经映射好的测试。结论是 PASS、FAIL、UNVERIFIED、ERROR，和架构检查分开。

没有配置业务需求图时，`check`、`baseline` 和验收的结果与退出码保持原样。

---

## 3. 业务需求图

### 3.1 模型

`sextant.json` 的 `businessRequirements` 是唯一可写来源。实体种类和 id 前缀必须一致：

| 种类 | 前缀 | 含义 |
| :--- | :--- | :--- |
| requirement | `BR-` | 需求 |
| flow | `FLOW-` | 流程 |
| rule | `RULE-` | 规则 |
| event | `EVENT-` | 事件 |
| state | `STATE-` | 状态 |
| test | `TC-` | 验收 |
| code | `CODE-` | 代码锚点 |

关系类型只有：`includes`、`triggers`、`constrains`、`produces`、`affects`、`implemented_by`、`verified_by`。每条关系指向两个已经存在的实体。同一对实体不能有两种关系类型。简写列表（`flows`、`trigger`、`preconditions`、`rules`、`effects`、`acceptance`）只能写在需求上，写在其他种类上则校验失败并点名该实体。

代码实体可以声明 `source`。测试实体可以声明 `checkId`；若验收配置存在而这个 id 不在其中，加载配置失败，这个失败不是验收 FAIL。实体可以带未关闭问题的原文。

### 3.2 复核范围

`sextant-drift requirements <实体id>` 列出该实体的直接邻居，入边和出边都算。更远的路径不列入。输出先说明：这是已声明关系的复核范围，不是代码影响证明。

| 邻居 | 终端怎么写 |
| :--- | :--- |
| 代码，写了 `source` | `锚点已声明`，并打印路径 |
| 代码，没有 `source` | `锚点缺失` |
| 测试，没有 `checkId` | `锚点缺失` |
| 需求、流程、规则、事件、状态 | 只写 id、复核范围和关系，不写锚点 |

未配置 `businessRequirements`，或图无法加载时，命令以退出码 2 结束。清单本身不分析源码，也不改变 `check` 的通过与否。

### 3.3 报告里的读法

业务区是一份目录加一张邻居图。

- 目录只列需求，按下面的排序。每行显示标题、未关闭问题数、缺锚点的邻居数。
- 默认焦点是按同一排序得到的第一个实体。有需求时，它就是编号最小的那条需求。
- 图只画焦点和它的直接邻居。点目录中的需求，或点邻居，焦点切换，图重画。
- 列从左到右固定为：需求；流程 / 规则 / 事件；状态；代码 / 验收。空列不占位，已有列的先后不改。
- 同列关系走卡片左侧的侧边通道。跨列关系走卡片上方的独立通道。箭头指向关系原来的目标，不因焦点改变而反过来。
- 卡片宽度固定，标题和问题在卡片内换行，原文保留。代码卡片显示已声明路径或「锚点缺失」；测试卡片显示 check id 或「锚点缺失」。
- 每张邻居图在生成报告时画好。页面脚本只切换可见的那一张。不加载脚本时，默认邻居图仍然显示。
- 报告记下三个数：实体数、SVG 总字节数、最大邻居数。
- 同一模型的 Mermaid 和 JSON 留在折叠区，作为全量投影。

排序在每一次生成里都相同：实体类型（需求、流程、规则、事件、状态、代码、验收），然后 id 里最后一段数字的数值，然后完整 id。没有数字，或数字超出安全整数的 id，排在有编号的 id 之后，再按完整 id 比较。`BR-002` 在 `BR-2` 前，`BR-2` 在 `BR-10` 前。

放不下的图要报渲染错误，并说明关系没有被删除。触发条件包括：类型没有对应的列、id 重复、问题或锚点字段不是文本、关系缺少端点或指向未知实体、结构化投影不是合法 JSON。这种情况下不输出一张少了边的 SVG。

### 3.4 这一版不做

不画整张关系总图。不把 id 前缀翻译成模块名。不提供矩阵、图上编辑、需求级 diff。不扫描仓库去补锚点。不把复核范围说成代码影响证明。不因为业务图改变 `check` 或 `verify` 的通过与否。

## 4. 架构门禁

`check` 读取 `sextant.json`，用 AST 提取实际依赖，对照分层和不变量。

必须捕获的违规：

- 跨层旁路
- 逆向依赖
- 循环依赖，并打印环上的文件
- 不变量命中的禁止导入，以及规则写明的其他确定性匹配

每条违规要带类型、严重级别、文件和行号、匹配到的证据、被违反的规则。`check --json` 把同一结果打到标准输出。

退出码：`0` 通过（含基线已豁免的旧违规）；`1` 有新的偏航；`2` 配置或解析失败。

`init` 扫描现有目录，写出 `sextant.json`，并导出只读的 `ARCHITECTURE.md`。`baseline` 把当前违规收进 `.sextant/baseline.json`。之后 `check` 只把基线之外的违规当作新偏航。

`check` 不发起网络请求，不改工作区里的源码。

---

## 5. 验收证据

`acceptance` 是另一段配置。它把需求映射到测试文件和测试全名。`verify` 在本地跑这些测试。

| 状态 | 退出码 | 含义 |
| :--- | :--- | :--- |
| PASS | 0 | 必要检查有当前证据且通过，语义确认也匹配 |
| FAIL | 1 | 当前证据里有失败的检查，或架构检查未通过 |
| ERROR | 2 | 配置、证据或执行器出错 |
| UNVERIFIED | 3 | 缺证据、缺确认，或映射不完整 |

结构合规不能推出行为已经满足。缺证据保持 UNVERIFIED。测试失败的位置留在测试上，不改写成业务源码违规。业务图里的测试链接不参与这次打分。

---

## 6. 审查报告

`report` 写出自包含的 `drift-report.html`，默认中文，可用 `--lang en`。架构图画 C4 容器与组件，原生 SVG，零外部脚本。业务区按第 3.3 节呈现。报告只读：它不回写 `sextant.json`。

---

## 7. 验收标准

下面每条都有对应测试，且描述的是当前行为。

1. 同一份业务图连续生成两次报告，默认焦点、节点顺序和 SVG 一致。
2. 聚焦任一实体时，图上的其他节点正好是它的直接邻居；边的方向与声明相同，不出现未声明的边。
3. 同列边走侧边通道，跨列边走上方通道；列顺序不因连线而改变。
4. `BR-2` 排在 `BR-10` 前；流程、规则、事件按种类排，不按编号混排。
5. 不加载页面脚本时，默认邻居图可见。
6. 某个代码缺路径或某个测试缺 check id 时，其余邻居仍然显示，并标明锚点缺失。
7. 给同一份架构结果附上业务图之后，违规条数和判定文本不变。
8. 类型无法放入四列时，报告给出渲染错误，折叠区仍保留原来的关系。
9. 未配置业务图时，`check` 的通过与否与未引入该字段时相同。
