# SextantDrift 项目重启白皮书：设计精华、踩坑复盘与全新架构蓝图

> **版本**：v2.0 Reboot Edition (2026)  
> **核心定位**：面向 AI Coding 与现代工程团队的「架构 X 光机与偏航检测罗盘（Architecture X-Ray & Drift Compass）」  
> **一句话战略**：调换切入顺序、挂靠现有 Spec 生态、弃绝 Agent 自证幻觉、聚焦确定性结构与语义不变量、CLI / CI 门禁先行。

---

## 第一部分：保留的设计精华 (The Golden Essence)

在过去的探索与讨论中，SextantDrift 沉淀出了极高价值的底层认知与产品灵魂。这些资产在重启后将被完整继承并放大：

### 1. 终极灵魂：「永远只看两张图的红绿差分」 (Design by Diagram, Diff by Diagram)
- **痛点对齐**：2026 年的核心矛盾是“人审不过来 AI 代码”（PR 人工审核耗时翻 5 倍，积压超百万行未审代码）。行级的 `git diff` 支离破碎，开发者陷入细节泥潭；而死图（Miro / Draw.io）画完即弃，管不住代码。
- **唯一视觉心智**：
  - **左屏（Target）**：设计意图（你怎么设计的）
  - **右屏（Actual）**：代码实际拓扑（代码怎么实现的）
  - **标红区（Drift Alert）**：两张图的红线夹角与违规连线。
- **价值**：开发者不再肉眼逐行审查几百行黑盒代码，而是像看心电图/X光片一样，一眼识别架构是否偏航。

### 2. 极简表达律：80% 图 + 20% Rules
- **抛弃文字 PRD 巨石**：成百上千行的文字需求文档，开发者懒得写，AI 读多了迷失上下文。
- **图定骨架（80%）**：图形天然定义了模块边界、执行次序与生命周期。
- **规则定灵魂（20%）**：图表达不了非功能性约束与事务边界，因此图旁边永远伴随 3~5 条硬性约束（Invariants），由规则补足死图无法表达的语义。

### 3. 语义不变量（Invariants）作为一等公民
- 简单的结构图或依赖分析器（如 ArchUnit）只能看文件从属关系。
- 真正导致生产灾难的往往是**语义时序破坏**（如“未落库直接调用耗时 AI 接口丢数据”、“第三方调用未包裹超时与重试降级”、“Controller 越界直连 ORM 模型”）。
- 把 Invariants 规则提升为与图平级的核心支柱，是 SextantDrift 区别于传统静态分析工具的核心护城河。

### 4. 零侵入共享文件协议 (Zero-Intrusion Protocol)
- 不搞脆弱的终端拦截（pty hook）。
- 不搞私有 IDE session 日志逆向解析。
- 不搞黑盒私有网络通信。
- **只以代码仓库中 Git 纳管的标准纯文本（Markdown + Mermaid + YAML）为总线**。对任何支持文件读写的 AI Agent（Claude Code, Cursor, Copilot, Codex）均天然兼容。

### 5. 核心技术与产品形态彻底解耦
- 核心引擎是纯粹的**架构因果拓扑差分与 AST 分析引擎**。
- 产品形态是易变的：它可以是 `npx sextant-drift check`（CI 门禁）、可以是单文件独立 HTML 审查报告、可以是 VSCode/Cursor 插件、最后才考虑桌面端。

## 第二部分：深度踩坑与误区复盘 (The Pitfalls & Lessons Learned)

回顾第一版尝试之所以搁浅，关键不是“方向不对”，而是在**技术切入顺序、边界设定、标准定位与交付形态**上踩了 6 个致命的坑：

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           第一版尝试踩下的 6 大致命陷阱                      │
├────────────────────────────────┬────────────────────────────────────────────┤
│ 陷阱 1: 切入顺序严重倒置       │ 把 3/10 难度的时序因果当第 1 步，稳妥的模块放背景 │
│ 陷阱 2: Agent 自证即幻觉       │ 依赖 Agent 回写 actual-sequence.md（幻觉套娃）     │
│ 陷阱 3: 脆弱静态推断与假阳性   │ 试图用简单正则/静态分析猜 async 真实运行时序       │
│ 陷阱 4: 另立 spec.md 孤岛标准   │ 忽视 GitHub Spec Kit / AGENTS.md 既有生态          │
│ 陷阱 5: "每个功能画4张图"高门槛│ 强迫人类写代码前先画图，违反开发者真实工作习惯     │
│ 陷阱 6: 沉重桌面端与历史包袱   │ 被 Tauri/编辑器插件拖死，核心引擎无法进入 CI       │
└────────────────────────────────┴────────────────────────────────────────────┘
```

### 踩坑 1：切入顺序严重倒置（把最难的当第一步）
- **复盘**：技术可行性评估中，“模块/依赖级差分”成熟度为 **8/10**，“状态机死锁检查”为 **7/10**，而“时序因果级差分”只有 **3/10**。第一版产品宪章却将最难的时序差分作为核心宣传点与 MVP 交付目标，把确定性最高的模块依赖当成可有可无的背景。
- **后果**：直接撞上时序提取的硬墙，导致核心引擎迟迟无法给用户提供可信的体验。
- **教训**：**先做“架构 X 光机”（结构+规则+状态），再做“六分仪”（因果时序）**。先用 100% 确定性、零误报的基础能力占领用户心智。

### 踩坑 2：Agent 回写 actual-sequence.md 是“自证即幻觉”
- **复盘**：第一版曾设想“Agent 编码完成后，自行反思并生成实际时序图 `actual-sequence.md` 写入目录”。
- **实质**：**这是让嫌疑人自己给自己写结案报告**。如果 Agent 漏写了落库步骤，它在回写时序时由于幻觉或自我防御，大概率会写“我先落库了再调 AI”，或者完全复述设计图。
- **教训**：**绝对不能依赖 Agent 自述作为代码验收凭据！** 实际拓扑必须来自机器对代码或运行时的确定性提取。

### 踩坑 3：纯静态粗暴推断运行时代价惨重（假阳性噩梦）
- **复盘**：试图仅通过静态 AST 正则或调用图直接判定异步执行时序。
- **实质**：现代代码充满 `Promise.all`、事件总线发布订阅、依赖注入（DI）、回调函数、中间件流水线。纯静态推断在时序因果上必然产生大量假阳性（误报）。
- **后果**：在开发者工具领域，**误报等于自杀**。开发者一旦看到两次虚假的报警，就会彻底卸载工具。
- **教训**：时序因果检测必须建立在**高精度动态测试 Trace**（测试运行录制）上；静态分析在 v1 阶段只做结构与层级判定，不强行给出不可信的时序结论。

### 踩坑 4：闭门造车另立 spec.md 孤岛标准
- **复盘**：设计了私有的 `.sextant/features/01-xxx/spec.md` 目录规范，试图让全球开发者接受一种全新的 Spec 组织形式。
- **实质**：GitHub Spec Kit、OpenSpec、`AGENTS.md` 已成为主流。再立新标准是必输之战。
- **教训**：**做适配器与校验层，不做孤岛标准**。只要项目里有 `AGENTS.md`、`.github/spec-kit` 或包含 Mermaid 的 Markdown，SextantDrift 都能一键读取并校验。

### 踩坑 5：“必须先画 4 张图”的高门槛阻碍采用
- **复盘**：要求人类在写任何代码前，手动画出 Flow、Sequence、Module、State 四张图。
- **实质**：采用友好度评分仅 **4/10**。独立开发者宁可直接写代码，也不会为了一个小功能花 20 分钟画 4 张图。
- **教训**：颠覆输入流向 —— **“逆向推导 + 增量锁定”**：
  - **模式 A（逆向 X 光）**：开发者已有代码，一键 `npx sextant-drift init`，自动反向扫描推导出当前架构图与 Invariants 骨架，人类只需审阅确认。
  - **模式 B（AI 代劳）**：给 AI 一句话提示词，AI 帮人生成骨架图与约束，人类只花 30 秒“勾选与确认”。

### 踩坑 6：过早陷入沉重的 Tauri 桌面端与无关插件
- **复盘**：从一个臃肿的通用桌面文本编辑器模板起步，内部混杂了番茄钟、插件市场、ProseMirror 复杂排版等大量无关代码。
- **实质**：把 90% 的精力消耗在桌面窗口、UI 样式、IPC 通信上，核心差分引擎反而成了 toy implementation（简单的正则切割）。
- **教训**：**彻底弃用既有桌面杂项代码，实行 Core-First（无头核心先行）**。以可以跑在 CI / 终端的轻量 CLI 为第一核心，UI 仅作为轻量渲染层。

### 2. 核心引擎三大支柱实现机制

#### 支柱一：确定性模块与层级漂移引擎 (Module & Layer Drift Engine)
- **输入**：源码文件目录 + 设计中的模块图（或分层规则声明）。
- **分析方式**：利用 TypeScript 编译器的 AST 解析所有 `import`、`require` 与 `export from`，构建有向依赖图（Directed Acyclic Graph / DAG）。
- **捕获违规**：
  - **跨层旁路（Bypass）**：例如 Controller 直接引入了 Repository，绕过了 Service 业务层。
  - **逆向依赖（Inversion）**：底层领域模型反向依赖了高层 UI/Web 模块。
  - **循环依赖（Cycles）**：模块 A 与模块 B 形成了循环强依赖。
- **输出**：确定性的违规边清单，并在生成对比图时将违规连线标为亮红粗线。

#### 支柱二：语义不变量规则引擎 (Semantic Invariants Engine)
- **输入**：`spec.md` 或 `AGENTS.md` 中的伴随规则（Invariants）。
- **规则规范格式（YAML 或语义标签）**：
  ```yaml
  invariants:
    - id: PERSIST_BEFORE_EXTERNAL
      severity: critical
      desc: "用户输入必须先持久化落库，方可发起外部 LLM 或支付等不可靠网络调用"
      pattern:
        must_precede: ["db.save", "repository.create"]
        target: ["llmService.call", "aiClient.chat", "payment.charge"]
        scope: "api/controllers"

    - id: FORBID_DIRECT_DB_IN_UI
      severity: critical
      desc: "UI 组件与表现层严禁直接调用数据库驱动或 ORM 实例"
      pattern:
        forbid_import: ["@prisma/client", "typeorm", "pg", "mysql2"]
        in_path: "src/views/**,src/components/**"

    - id: MANDATORY_FALLBACK_TIMEOUT
      severity: warning
      desc: "所有第三方外部 API 调用必须设置超时时间与 catch 兜底处理"
      pattern:
        target: ["fetch", "axios.*"]
        require_config: ["timeout"]
  ```
- **工作机制**：在源码 AST 遍历对应函数的语句列表，校验关键动作的前提条件是否满足，直接捕捉致命的逻辑顺序漏洞。

#### 支柱三：状态机完整性检测引擎 (State Machine Verifier)
- **输入**：Mermaid `stateDiagram-v2` 源码。
- **校验逻辑**：
  - **黑洞状态（Deadlock / Black Hole）**：状态有入度无出度，且并非显式的 `[*]` 终止态。
  - **孤立状态（Unreachable Island）**：状态在图中无任何可达路径。
  - **缺失兜底跃迁（Missing Error Transitions）**：异步等待类状态（如 `Processing`, `Submitting`）缺乏 `Failed`, `Timeout`, 或 `Retry` 的出口。
- **输出**：在状态机渲染图中直接高亮标记异常节点。

## 第五部分：终极检验准则 (The Litmus Test)

重构完成后的 SextantDrift 必须能通过以下三个苛刻的体验检验：

1. **五秒原则**：在任何合规或违规的项目根目录下敲下 `npx sextant-drift check`，5 秒内给出清晰的彩色红绿判定与明确的违规代码行指引。
2. **零幻觉原则**：给出的每一条架构违规，都有确凿的代码 AST 或规则证据，杜绝任何基于 LLM 猜测产生的假阳性。
3. **一眼看懂原则**：打开 `drift-report.html`，即使不看任何文字说明，一个初级工程师仅凭左边正常绿线、右边异常红线的双图夹角，就能在 10 秒内说出系统哪里偏航。
